# VPN-пресеты с переносимыми подписками

Установщик для личного VPS: готовая **3x-ui** и **Xray-core**, один из двух пресетов, HTTPS и базовый firewall. **В режиме `names` тот же домен, путь подписок и имя пользователя дают ту же ссылку при новой установке.** Для переноса всех ключей и актуальных настроек панели предусмотрен `instance.json`. Новые установки используют HTTPS на стандартном порту 443; у REALITY есть собственный статический сайт.

На чистом VPS с Ubuntu 24.04 выполните **под root**, предварительно направив оба DNS-имени на сервер и заменив домены, email, имена пользователей и заглушки путей на свои:

```bash
curl -fsSL https://raw.githubusercontent.com/Dmitriy129/self-variants/main/bootstrap.sh | bash -s -- --profile reality --domain panel.example.com --site-domain site.example.com --email admin@example.com --fingerprint firefox --site-template random --monitoring destinations --users owner,family-1,family-2 --subscription-ids names --subscription-path '<YOUR_SUBSCRIPTION_PREFIX>' --panel-path '<YOUR_PANEL_PREFIX>'
```

`<YOUR_SUBSCRIPTION_PREFIX>` и `<YOUR_PANEL_PREFIX>` — заглушки: замените их целиком, включая угловые скобки, двумя разными постоянными префиксами. Можно передать `segment` или `/segment/`; установщик добавляет начальный и конечный `/`. Используйте латинские буквы, цифры, `_` и `-`. Сохраните готовую команду в защищённом месте и повторяйте её с **теми же путями**.

Префикс подписок — общая секретная часть ссылок: **кто знает этот префикс, может перебирать имена пользователей и получать их VPN-профили**. Имена в URL не скрываются. Не публикуйте рабочий префикс или готовую команду. Режим `names` включается явно; по умолчанию `--subscription-ids random`, путь подписок `/sub/`, а путь панели случайный. Такие случайные ссылки сохраняются при переносе через `instance.json`.

Предварительно загружать архив не нужно. `bootstrap.sh` скачивает пакет релиза **v0.1.3**, проверяет его SHA-256 по встроенному значению, сохраняет установщик в `/opt/vpn-installer/releases/v0.1.3` и передаёт указанные аргументы в `install.sh`. Постоянный путь для обслуживания — **`/opt/vpn-installer/current/install.sh`**. Эта команда включает журнал назначений; для базовых показателей без такого журнала используйте `--monitoring basic`.

| Пресет | VPN | Клиент |
|---|---|---|
| `reality` | VLESS + REALITY + XTLS Vision, TCP 443 | актуальный v2rayNG |
| `hysteria2` | Hysteria2 + TLS, UDP 443 | актуальный v2rayNG с поддержкой Hysteria2 |

Один VPS — один пресет. Оба используют Xray; AmneziaWG в эту версию не входит. Подписка выдаётся самой 3x-ui в Base64. Существующий `subs-resolver` получает её URL без изменений своего кода.

## Требования

- Чистая **Ubuntu 24.04 LTS x86_64**, systemd, root/sudo и Python 3.12 из ОС; для загрузки одной командой нужен `curl`.
- Прямой публичный адрес на сетевом интерфейсе VPS. NAT и CDN-проксирование не поддерживаются.
- Для `reality` нужны **два разных имени**: домен панели/подписок и домен сайта/REALITY. Подойдут два поддомена одного домена или имена в разных доменах. Оба должны указывать прямо на один VPS, без CDN-проксирования.
- Для `hysteria2` нужен один домен панели/подписок и VPN; отдельный сайт не устанавливается.
- Все A/AAAA используемых имён должны указывать на эту машину перед выпуском сертификатов. Ненужные AAAA-записи нужно удалить.
- На firewall хостинга разрешены текущий SSH-порт, TCP 80 и TCP 443; для `hysteria2` дополнительно UDP 443. При восстановлении старого файла схемы 1 нужен также TCP 8443.

Установщик не импортирует чужую установку 3x-ui, существующие сайты Nginx или пользовательские правила UFW. DNS меняется у вашего провайдера вручную. Сам установщик не покупает и не заменяет VPS.

## Первая установка

Для REALITY используйте команду в начале README. Для Hysteria2 на **другом чистом VPS**, также под root:

```bash
curl -fsSL https://raw.githubusercontent.com/Dmitriy129/self-variants/main/bootstrap.sh | \
  bash -s -- --profile hysteria2 --domain hy2.example.com \
  --email admin@example.com --users owner,family-1,family-2 \
  --subscription-ids names --subscription-path '<YOUR_SUBSCRIPTION_PREFIX>' \
  --panel-path '<YOUR_PANEL_PREFIX>'
```

Все обязательные параметры передаются заранее, поэтому интерактивных вопросов не будет. Пароли и ключи создаются автоматически. Если предварительные условия не выполнены, установщик завершится с объяснением ошибки. Команды запускаются **на VPS**; на локальном компьютере достаточно сохранить копию настроек.

Имена из `--users` становятся стартовым списком пользователей. Если список не задан, публичный релиз создаёт пользователя `personal`. Адрес панели, пароль администратора и отдельный URL подписки каждого пользователя выводятся после успешной установки. В режиме `names` ссылка имеет вид `https://panel.example.com/ВАШ_ПРЕФИКС/owner`, без явного `:443`. Остальных пользователей можно добавлять через панель. Используйте один созданный inbound: базовые параметры транспорта и внешнего адреса обслуживает установщик.

По умолчанию новая установка использует `--monitoring basic`: в панели доступны трафик, текущие IP подключений и время последней активности пользователей. Для записи адресов назначений при первой установке передайте `--monitoring destinations`; режимы и ограничения описаны ниже.

С версии **v0.1.3** новая установка REALITY использует отпечаток **`firefox`**. Чтобы выбрать его явно, добавьте `--fingerprint firefox` к команде с `--profile reality`; другое значение, например `--fingerprint chrome`, также можно передать. Имя должно поддерживаться Xray в клиентском приложении: установщик проверяет формат имени, но не совместимость каждого клиента. Этот параметр действует только при создании установки. Повторный запуск сохраняет значение из панели; для Hysteria2 параметр не применяется.

На работающем сервере откройте созданный inbound → настройки REALITY → **uTLS / Fingerprint**, выберите нужный отпечаток и сохраните. Если в **Hosts** у этого inbound заполнен **Fingerprint**, он имеет приоритет; пустое поле наследует значение inbound. Пользователям нужно обновить подписку и переподключиться: в полученном профиле изменится `fp`, а URL подписки останется прежним. Отдельно импортированный статический профиль автоматически не обновляется.

После установки откройте **полный адрес панели**, включая её путь, и войдите с напечатанными логином и паролем. В v2rayNG добавьте группу подписки с URL из строки «Подписка», обновите группу и выберите профиль. Для `subs-resolver` этот же URL служит HTTP-источником. Пароль администратора относится к панели, а не к приложению VPN. Эти шаги также печатаются в консоль.

**Для полного восстановления дополнительно сохраните `/etc/vpn-installer/instance.json` вне VPS.** Файл содержит секреты и создаётся с правами `0600`. Не отправляйте его в Git, публичные чаты или трекеры задач. URL подписки также предоставляет доступ к профилям пользователя.

### Альтернатива: архив или исходники

Можно вручную загрузить архив из [релиза v0.1.3](https://github.com/Dmitriy129/self-variants/releases/tag/v0.1.3) или скопировать исходники проекта на VPS. Распакуйте архив и перейдите в папку с `install.sh`, `versions.json`, стартовым списком `users.json` или `users.example.json`, `vpn_installer/` и `sites/`:

```bash
sudo bash install.sh --profile reality \
  --domain panel.example.com --site-domain site.example.com \
  --email admin@example.com --users owner,family-1,family-2 \
  --subscription-ids names --subscription-path '<YOUR_SUBSCRIPTION_PREFIX>' \
  --panel-path '<YOUR_PANEL_PREFIX>' </dev/null
```

При запуске `sudo bash install.sh --profile reality` из терминала мастер запросит недостающие домены и email. Если шаблон не указан, один из четырёх вариантов выбирается случайно без дополнительного вопроса. При ручной установке обслуживайте сервер через `install.sh` из сохранённой папки проекта; путь `/opt/vpn-installer/current/` создаётся загрузчиком `bootstrap.sh`.

## Собственный сайт REALITY

Обычный браузер открывает `https://site.example.com/` и получает статическую страницу с доверенным TLS-сертификатом. Клиент REALITY подключается к тому же имени и TCP 443; Xray проверяет его авторизацию и обслуживает VPN-соединение. TLS-запросы без авторизации REALITY передаются локальному сайту.

Доступны четыре самостоятельных одностраничных шаблона без JavaScript, внешних ресурсов, форм и аналитики:

| `--site-template` | Содержание |
|---|---|
| `field-notes` | Заметки о растениях и наблюдениях на прогулке |
| `ceramic-studio` | Личный журнал керамики и работы с материалами |
| `trail-journal` | Небольшие зарисовки о пеших прогулках |
| `reading-room` | Заметки о чтении и книгах |

Можно явно передать `--site-template random` или опустить этот параметр: случайный выбор происходит **один раз при создании установки**, а в переносимый файл записывается конкретное имя шаблона. Повторный запуск на той же машине и восстановление через `--config` не выбирают его заново. На новом VPS без `--config` случайный шаблон может отличаться. Для фиксированного варианта передайте имя из таблицы. Домен `--site-domain` остаётся обязательным.

Выбор хранится в `instance.json` как `site.template`; домен сайта — как `site.domain`. После установки страницу можно редактировать в `/var/www/vpn-site/index.html`. Повторный запуск сохраняет существующий файл. При переносе на чистый VPS установщик восстановит исходный шаблон выбранного вида; **свои изменения HTML нужно сохранить и скопировать отдельно**. Команда `--backup` пока не включает файлы сайта. Подробнее о шаблонах — в [sites/README.md](sites/README.md).

## Новый VPS: повтор команды с теми же ссылками

Начиная с v0.1.1, `--subscription-ids names` позволяет заново установить VPN на чистый VPS без старого `instance.json` и получить прежние URL подписок. `subId` равен **точному имени пользователя, включая регистр**. Имена в этом режиме должны состоять из 1–128 символов `A–Z`, `a–z`, `0–9`, `_`, `-`. При том же домене панели, `--subscription-path` и имени ссылка совпадает символ в символ. Постоянный `--panel-path` также сохраняет адрес панели.

1. Возьмите сохранённую команду с `--subscription-ids names`, прежними путями и доменами, актуальным списком `--users`.
2. Вручную направьте A/AAAA прежних имён на новый VPS. Для REALITY нужны оба имени: панели и сайта. Дождитесь обновления DNS перед выпуском сертификатов.
3. Выполните сохранённую команду на **новой чистой машине**.
4. Обновите существующую группу подписки в v2rayNG: её URL остаётся прежним, а клиент получит новые параметры подключения. URL источника в `subs-resolver` также не меняется.

При таком повторе **UUID, пароли подключения, ключи и short ID REALITY, пароль администратора создаются заново**. Для подключения к новому серверу успешно обновите группу подписки и используйте обновлённый VPN-профиль. Сервер не отправляет настройки клиентам сам: автоматическое обновление происходит только если оно включено в приложении. Кэш DNS и интервал обновления подписки могут вызвать перерыв в доступе; бесшовное переключение не гарантируется.

Повтор стартовой команды создаёт пользователей из `--users` с начальными настройками. Изменённые в панели лимиты, сроки действия и отключения так не восстанавливаются: в частности, отключённый пользователь из стартового списка снова будет включён. Удалите ненужные имена из команды и поддерживайте список актуальным. Пользователю, добавляемому через панель, для читаемой ссылки задайте **Subscription ID равным его имени** и добавьте это имя в сохранённую команду. Если оставить случайный Subscription ID панели, такая ссылка воспроизводится только через `--config`. Для точного переноса ограничений и состояний пользователей также используйте экспорт и `--config` ниже.

На уже установленном сервере и при восстановлении через `--config` параметры `--subscription-ids`, `--subscription-path` и `--panel-path` **не меняют действующие URL**: используются сохранённые значения. Случайные ссылки, в том числе созданные в v0.1.0, не превращаются в ссылки с именами автоматически. Для сохранения таких ссылок нужен прежний `instance.json` или его резервная копия.

## Полное восстановление через instance.json

**Тот же `instance.json` + прежние домены = те же ссылки и ключи подключения.** Этот способ переносит актуальных пользователей панели, их ограничения и состояния, поэтому клиенту не требуется получать новые ключи из подписки.

На старом VPS сначала экспортируйте актуальные данные, особенно если меняли пользователей через панель:

```bash
sudo bash /opt/vpn-installer/current/install.sh --export-config /root/instance.json
```

Перенесите этот файл на новую машину. Под root можно загрузить установщик и подготовить VPS **до переключения DNS**:

```bash
curl -fsSL https://raw.githubusercontent.com/Dmitriy129/self-variants/main/bootstrap.sh | \
  bash -s -- --config /root/instance.json --prepare
```

Подготовительный запуск устанавливает компоненты и открывает HTTP-проверку сертификата. VPN и HTTPS ещё не готовы. Теперь переключите A/AAAA прежних имён на новый VPS — для REALITY схемы 2 это **и домен панели, и домен сайта** — дождитесь обновления DNS и завершите установку:

```bash
sudo bash /opt/vpn-installer/current/install.sh --config /root/instance.json
```

Переносимый файл сохраняет версию схемы, домены, внешний HTTPS-порт, пути панели и подписки, `subId`, UUID/пароли пользователей, ключи и short ID REALITY, включение, лимиты и сроки действия пользователей. На новой машине создаётся новая БД; старая БД для этого сценария не нужна. TLS-сертификаты выпускаются заново на прежние имена, привязки к отпечаткам сертификатов нет. Изменённую страницу сайта перенесите отдельно.

Экспорт и восстановление отпечатков требуют установщика **v0.1.3 или новее**. `reality.fingerprint` хранит значение inbound, а необязательное `reality.host_fingerprint` — переопределение в его Host. Экспорт читает оба значения из панели; после очистки переопределения поле `host_fingerprint` исчезает и сохраняется наследование. Старые файлы без `fingerprint` восстанавливаются с прежним `chrome`, а не с новым значением по умолчанию. При `--config` используются значения файла; добавлять `--fingerprint` к восстановлению нельзя.

После обновления DNS существующая группа v2rayNG использует тот же URL. Внешняя ссылка редиректора также не меняется, потому что URL его источников остаются прежними. Во время распространения DNS старый и новый адреса могут временно использоваться разными клиентами; старый сервер лучше оставить доступным до проверки новой машины.

Если ссылки создавались случайно и потеряны и переносимый файл, и резервная копия, восстановить неизвестные токены невозможно. Для ссылок в режиме `names` достаточно прежнего домена, пути подписок и точных имён пользователей. Сам домен случайные токены не определяет.

### Совместимость со старыми установками

Новые файлы имеют `schema_version: 2`: панель и подписки доступны на TCP 443, URL не содержит `:443`, а REALITY использует свой сайт. Файлы с `schema_version: 1` восстанавливаются в прежней схеме: панель/подписки на **8443**, URL содержит **`:8443`**, REALITY использует сохранённый внешний TLS-сайт. Идентификаторы и ссылки остаются прежними.

Автоматической миграции схемы 1 в схему 2 нет: смена порта меняет URL подписки. Обычный повторный запуск и перенос с `--config` сохраняют исходную схему; добавление нового сайта к старой установке таким способом не выполняется.

## Пользователи и повторный запуск

- Для первой установки передайте имена через `--users owner,family-1,family-2` или укажите JSON-файл через `--users-file /root/family.json`. Эти два параметра взаимоисключающие. Формат файла — обычный массив имён, например `["owner", "family-1", "family-2"]`; в нём нет паролей или ключей. Имена служат подписями в панели, отдельными логинами администратора они не являются.
- Публичный стартовый список репозитория — `users.example.json` с содержимым `["personal"]`. Личный `users.json` исключён из Git. При запуске из исходников без `--users` и `--users-file` читается локальный `users.json`, если он есть, иначе — публичный пример. В пакет релиза `users.json` создаётся из `users.example.json`, поэтому личный список в релиз не попадает.
- Для каждого имени создаются собственные ключи подключения и URL подписки. В режиме `names` при тех же домене и пути URL воспроизводится при новой установке, а ключи создаются заново; при восстановлении через `--config` сохраняются и URL, и ключи. Каждому члену семьи передайте его ссылку; в панели можно независимо отключать пользователей и задавать им лимиты.
- Стартовый список применяется **только при создании новой установки**. Повторный запуск, продолжение `--prepare` и восстановление через `--config` не читают его заново. Если меняли список после установки, добавляйте или удаляйте пользователей в панели.
- После первой установки текущие пользователи принадлежат панели. Повторный запуск экспортирует актуальное состояние и **не применяет старый список пользователей поверх нового**.
- `email` пользователя в 3x-ui — идентификатор; реальный почтовый ящик для него не требуется. Верхний `email` файла нужен Certbot.
- `total_gb` сохраняет название поля 3x-ui, но значение задано **в байтах**; `expiry_time` — Unix-время в миллисекундах. Ноль означает отсутствие соответствующего ограничения.
- `limit_ip` переносится как настройка панели; применение ограничения числа IP требует отдельно настроенного fail2ban. Установщик его не включает, значение по умолчанию — `0`.
- После добавления, удаления, отключения пользователя, изменения его ключей или отпечатка REALITY обновите внешнюю копию через `--export-config`.
- Дополнительные inbounds, hosts, внешние ссылки, автоматические сбросы лимитов, HWID и другие настройки вне двух базовых пресетов не входят в переносимый формат. Экспорт откажется от неподдерживаемых изменений, которые умеет обнаружить. Для произвольной настройки используйте полную резервную копию БД, не полагайтесь на переносимый файл.
- Если сменили логин или пароль администратора, обновите `panel.username`/`panel.password` в защищённом `/etc/vpn-installer/instance.json`: API не возвращает пароль в открытом виде. Смена путей панели или подписки вручную требует согласованной перенастройки Nginx, поэтому такие изменения следует делать через перенос на чистый VPS.

Проверка файла без изменения системы (можно на локальном компьютере с Python 3.10+ и OpenSSL):

```bash
bash install.sh --check-config ./instance.json
```

Неполный файл не дополняется новыми случайными ключами. Проверка завершается до установки пакетов и изменений firewall.

## Мониторинг подключений

| Режим | Данные |
|---|---|
| `basic` — по умолчанию | Счётчики трафика, текущие IP подключений и последняя активность пользователей в 3x-ui |
| `destinations` | Базовые показатели и журнал соединений Xray с известными ему адресами назначения: доменами **или** IP |

Чтобы включить журнал назначений сразу при установке, добавьте `--monitoring destinations`, как в первой команде README. Например, под root:

```bash
curl -fsSL https://raw.githubusercontent.com/Dmitriy129/self-variants/main/bootstrap.sh | \
  bash -s -- --profile reality --domain panel.example.com --site-domain site.example.com \
  --email admin@example.com --monitoring destinations --users owner,family-1,family-2 \
  --subscription-ids names --subscription-path '<YOUR_SUBSCRIPTION_PREFIX>' \
  --panel-path '<YOUR_PANEL_PREFIX>'
```

Параметр `--monitoring` применяется только при создании новой установки; он также доступен для `hysteria2`. На уже установленном сервере режим меняется отдельной командой:

```bash
sudo bash /opt/vpn-installer/current/install.sh --set-monitoring destinations
sudo bash /opt/vpn-installer/current/install.sh --set-monitoring basic
```

Переключение сохраняет пользователей, их ключи и ссылки подписок. Переход на `basic` прекращает запись новых назначений; ранее сохранённые архивы остаются до удаления по правилам хранения.

В режиме `destinations` Xray пишет `/var/log/x-ui/access.log`. В панели раздел **Xray Log** показывает текущий журнал; текстовый фильтр помогает искать имя пользователя, IP или домен. Журнал IP клиента в панели охватывает недавние подключения за последние **30 минут**. Это список наблюдаемых сетевых адресов: он не определяет конкретные устройства и не является долговременной историей подключений.

Журнал назначений содержит адрес, известный Xray при установке соединения. Если клиент передал IP, доменное имя может отсутствовать. Содержимое HTTPS, текст страниц, пароли и полные URL внутри HTTPS не расшифровываются; анализ трафика для определения назначения (`sniffing`) остаётся выключенным. Эти записи не следует воспринимать как полный журнал посещённых страниц.

Сама 3x-ui очищает текущий access log раз в сутки и при превышении **64 MiB**. Поэтому отдельный сборщик раз в минуту сохраняет доступные новые записи в `/var/log/vpn-installer/history/`. История хранится **до 7 дней**, с ориентиром на общий предел **128 MiB**: при нехватке места старые записи удаляются раньше. Ограничения проверяются при сборе, поэтому между запусками объём может временно превышать предел. Если 3x-ui успела очистить журнал между двумя опросами, несобранные строки теряются; непрерывная история не гарантируется.

Для чтения сохранённой истории на сервере:

```bash
sudo bash /opt/vpn-installer/current/install.sh --show-logs --log-lines 100
sudo bash /opt/vpn-installer/current/install.sh --show-logs --log-user owner --log-lines 100
```

Во второй команде `owner` — имя пользователя из панели. Команды доступны только root. Каталоги журналов закрыты правами `0700`, файлы — `0600`.

В переносимом файле сохраняется только политика мониторинга:

```json
"monitoring": {
  "mode": "destinations",
  "retention_days": 7,
  "max_log_mb": 128
}
```

Новые установки содержат это поле с выбранным режимом. Старые файлы без `monitoring` восстанавливаются без добавления мониторинга; `--set-monitoring` рассчитан на установки, в которых это поле уже есть. Сами журналы не включаются ни в переносимый JSON, ни в `--backup`; нужную историю сохраняйте отдельно с теми же ограничениями доступа. После изменения режима обновите внешнюю копию `instance.json` через `--export-config`.

## HTTPS и безопасность

| Снаружи | Назначение |
|---|---|
| Текущие SSH-порты | Существующий доступ к серверу |
| TCP 80 | HTTP-проверка Certbot; для домена сайта также перенаправление на HTTPS |
| TCP 443 | HTTPS панели и подписок; у REALITY также VPN и собственный сайт |
| UDP 443 | VPN только в пресете `hysteria2` |

Для REALITY схемы 2 Nginx принимает TCP 443 и читает имя сервера из TLS-запроса (SNI), сохраняя шифрование до нужного сервиса:

| Имя в запросе | Локальный маршрут |
|---|---|
| Домен панели, например `panel.example.com` | Nginx HTTPS `127.0.0.1:7443` → панель `127.0.0.1:2053` или подписки `127.0.0.1:2096` |
| Домен сайта, например `site.example.com` | Xray REALITY `127.0.0.1:10443` → VPN для авторизованного клиента; для обычного HTTPS — сайт Nginx `127.0.0.1:9443` |

Для Hysteria2 схемы 2 Nginx обслуживает панель и подписки на TCP 443, а Xray принимает VPN на UDP 443. Для схемы 1 сохраняется прежний маршрут: HTTPS панели/подписок на TCP 8443, VPN на TCP 443 или UDP 443.

Все внутренние серверы слушают только loopback; их порты не открываются наружу. Nginx сохраняет пути запросов к панели и подпискам. Access logs **Nginx** выключены; error logs этих виртуальных серверов также не записывают URL с токенами. Журнал VPN-соединений Xray включается отдельно режимом `destinations`. При первичном запуске панели внешний доступ к её внутренним портам уже блокируется UFW.

Certbot единолично управляет сертификатами. REALITY схемы 2 получает **два отдельных сертификата** — для панели и для сайта. Hysteria2 использует сертификат своего единственного домена. `certbot.timer` продлевает их автоматически; deploy hook проверяет конфигурацию и перезагружает Nginx. При продлении сертификата сайта REALITY или сертификата Hysteria2 также перезапускается `x-ui`, что кратко прерывает соединения. Продление только сертификата панели REALITY не требует перезапуска Xray. Встроенный выпуск сертификатов панели включать не нужно.

UFW закрывает остальные входящие подключения для IPv4 и IPv6. Текущие SSH-порты разрешаются до включения firewall; SSH-аутентификация не меняется. Повторный запуск не удаляет правила, которые вы добавили вручную.

## Проверка, резервные копии и обновление

```bash
sudo bash /opt/vpn-installer/current/install.sh --status
sudo bash /opt/vpn-installer/current/install.sh --backup
```

Резервная копия создаётся в `/etc/vpn-installer/backups/` с правами `0600`: согласованный SQLite-снимок БД панели с историей трафика и счётчиками, переносимый файл и маркер установки. **HTML сайта и журналы назначений в неё не входят**; собственную страницу и нужную историю соединений сохраните отдельно. Для обычного переноса используется JSON; автоматическое восстановление полной БД в этом интерфейсе не реализовано.

Версии и SHA-256 официальных архивов 3x-ui и Xray находятся в `versions.json`; загрузчик проекта также проверяет SHA-256 своего закреплённого пакета. Обычный повторный запуск не обновляет бинарники VPN. После изменения и проверки закреплённых версий обновление выполняется явно:

```bash
sudo bash /opt/vpn-installer/current/install.sh --update
```

Перед обновлением создаётся резервная копия; на время проверки сохраняются прежние бинарники и снимок БД. При ошибке запуска выполняется откат. Обновление через интерфейс самой 3x-ui обходит эти проверки, поэтому для воспроизводимости используйте установщик.

Проверка продления на VPS:

```bash
sudo certbot renew --dry-run
```

Без `--run-deploy-hooks` эта команда проверяет ACME, но не запускает наш deploy hook. Обработчик продления отдельно проверяется автоматическими тестами; для полной приёмки нужен реальный выпуск/продление и проверка подключения.

## Проверки проекта

```bash
python3 -m unittest discover -s tests -v
```

Реальная интеграционная проверка запускается отдельно в изолированном Ubuntu-контейнере, без изменения сервисов или firewall хоста:

```bash
bash tests/run-integration.sh /tmp/self-variants-artifacts
```

Каталог содержит официальные `x-ui-linux-amd64.tar.gz` и `Xray-linux-64.zip` из закреплённых релизов. Их SHA-256 указаны в `versions.json`. Сценарий в `tests/integration.py` проверяет четыре сочетания: схемы 1 и 2 × пресеты REALITY и Hysteria2. Он получает подписки через публичный HTTPS-вход Nginx, проверяет сайт и разделение доменов, восстанавливает чистую БД с теми же ссылками и передаёт HTTP-трафик через настоящий Xray по IPv4 и IPv6. Также проверяется сохранение отзыва доступа после удаления всех пользователей.

Контейнерные проверки не заменяют приёмку на VPS: реальный ACME, загрузка systemd после перезагрузки, внешний firewall, Android v2rayNG и доступность из РФ проверяются на развёрнутых серверах. Текущий редиректор проверяет доступность HTTP-подписки, а не VPN-соединения; несколько протоколов не гарантируют защиту IP от блокировки.

## Структура

- `bootstrap.sh` — загрузка закреплённого релиза с проверкой SHA-256 и запуск установщика.
- `install.sh`, `vpn_installer/cli.py` — команды и этапы установки.
- `config.py` — переносимый формат и сохранение идентификаторов.
- `panel.py` — API закреплённой версии 3x-ui и два VPN-пресета.
- `system.py` — проверки машины, архивы, systemd и резервные копии.
- `network.py` — Nginx, Certbot и UFW.
- `monitoring.py` — приватный архив журнала, автоматическая очистка и чтение истории.
- `sites/` — четыре автономных шаблона статического сайта REALITY.
- `users.example.json` — публичный стартовый список `["personal"]`; `users.json` — необязательный локальный список, исключённый из Git.
- `versions.json` — версии и контрольные суммы.

Публичный архив собирается командой `python3 tools/build_release.py --update-bootstrap`. Она включает только явно перечисленные файлы, берёт стартовый список из `users.example.json` и записывает контрольную сумму в загрузчик. Сам загрузчик и его тесты остаются в репозитории, чтобы контрольная сумма не зависела от самой себя.

Официальные источники: [3x-ui 3.11.0](https://github.com/MHSanaei/3x-ui/releases/tag/v3.11.0), [Xray 26.11.9](https://github.com/XTLS/Xray-core/releases/tag/v26.11.9), [протоколы 3x-ui](https://github.com/MHSanaei/3x-ui/blob/v3.11.0/docs/content/docs/en/config/inbounds.mdx), [Certbot](https://eff-certbot.readthedocs.io/en/stable/using.html).
